# Backlog

**Started 2026-09-05.** Things found, agreed, or deferred during the build that
are not yet done. Ordered by what would cost the owner most, not by effort.

Anything here is either the owner's explicit decision to defer, or something an
agent found and recorded rather than fixed. Nothing here is speculative
polish — if it is on this list, somebody hit it.

---

## 1. Hint text is doing three jobs, and only one of them belongs on screen

**Owner, 2026-09-05, on the vendor edit sheet:** *"all this explanation makes
the page really busy. maybe we add an arrow explaining the text and by default
it's closed. Budget has similar logic. or maybe add a small i icon, press it,
brings text as a tooltip."*

Three kinds of text are conflated in the forms:

| Kind | Example | Where it belongs |
|---|---|---|
| Label | "Business number" | Always visible |
| Disambiguator | "Net days. 0 is cash on delivery, which is a different fact." | Always visible, **one short line** |
| Rationale | "chasing it in February from somebody who finished in August is how a filing gets late" | A docblock, or behind a press |

The third kind is an *argument for the design*. It is good thinking and it is
the reason the field exists — and it does not need re-reading every time
somebody edits a supplier's phone number.

**Root cause worth naming:** agents wrote their reasoning into the UI. The same
fault appeared on the assignment sheet (rebuilt), in success messages (see §2),
and here. It is a systematic habit rather than three accidents.

**Recommended order.** Delete first, disclose second. Roughly 60–70% of the
current text should not exist in any form; hiding it behind an icon only makes
the mess collapsible. Cut hard, then put the genuinely useful remainder behind
a press.

**Mechanism: press-to-reveal, not a hover tooltip.** There is no hover on a
phone and this product is used on site. Tooltips also hide content from screen
readers and from find-in-page unless built very carefully. A small `i` toggling
a short paragraph, closed by default, works on touch and stays accessible.
Budget Tracker's `GuidePanel`/`PageGuide` are the precedent, and
`2026-09-04-reuse-from-budget-tracker.md` §4.1 already flags them as "a help
system that is a product decision, not a styling one". This is that decision.

**Also:** the vendor sheet's Retire and Void sections each carry a full
paragraph, which is most of why it scrolls. They are one decision — stop using
this vendor — and could be one disclosure.

## 2. Success messages are paragraphs

Same root cause as §1. A cost code save says *"01-00 saved. Everything already
filed under it — rate items, quote lines, invoice lines — …"* and continues.
A success line should be "01-00 saved." and stop. Now visible in the banner
introduced by `bb6fd52`, which makes it worse: it is transient text nobody has
time to read.

## 3. Every screen has the same browser tab title

Measured: `/`, `/projects`, a quote and `/templates` all read
"Northgate Building Group — Quotes". Only `src/app/layout.tsx` sets a title, so
four tabs open on one job are indistinguishable — and the one saying "Quotes"
is the pipeline.

Fix: page-level `generateMetadata` on the record routes, **record first**,
because browsers truncate from the right and the tenant name is identical in
every tab. `/quotes/[id]` → `QT-2026-0001 — Kensington basement finish`;
`/projects/[id]/schedule` → `Schedule — P-0001`; and so on. Wants one commit
across all record routes rather than one screen at a time.

## 5. `/billing/[projectId]` highlights nothing in the nav

It matches no rail destination, so on that screen nothing is marked current.
Making `/billing` match Pipeline would be a lie to assistive technology. The
honest fix is routing: move it to `/projects/[id]/billing`, at which point the
existing `startsWith('/projects')` highlights Pipeline for free and the parent
link becomes structural rather than hand-supplied.

## 6. Create forms are split across two idioms

Vendors, expenses and schedule put "Add" in a header `SheetButton`. Rates, cost
codes, reminder rules, tax rates, users, templates and template lines put it in
an always-visible section at the page foot. Templates papers over the distance
with `#anchor` links from its header.

The edit idiom is now consistent everywhere (`e6bb0e4`); this is the remaining
inconsistency. Recommendation from the agent that did the audit, and mine:
header `SheetButton` for all of them. Deferred because it changes seven screens
the owner has not complained about.

## 7. Destructive actions with no confirmation

`voidLine` in `Worksheet.tsx` and the three `setQuoteStatus` header buttons fire
on a single press. Nothing is ever deleted, so none of these is unrecoverable —
but voiding a quote line by mis-tap is still a bad afternoon.

---

## 8. `SheetButton` loses typed work after a server refusal

It re-baselines its dirty snapshot on submit, so after a refusal a later
dismissal drops what was typed without asking. `EditSheet` does not have this
fault (its sheets close on success, so the only submit they survive is a refused
one). The shell has no signal for a *failed* submit the way it now has one for
success — `SAVED_EVENT` could gain a sibling.

---

## 9. Test-ordering fragility

`tests/db/expenses.test.ts` needs an `organization` row it does not create, and
`tests/integration/files.test.ts` truncates `organization` in its last test. The
full suite passes in its current order; run those two files alone in the wrong
order and the first fails for a reason that has nothing to do with what it
asserts. Tighten the truncate list or have the file seed what it needs.

## 10. The backup key hostage problem

**Sharper than anything in the licensing design, and already true.** The `age`
backup private key lives only with the maintainer, so a customer who walks away
holds a USB drive of backups he cannot read.
`2026-09-04-licensing-design.md` §5.5 proposes encrypting to two recipients and
handing the customer his private half on paper with the hardware, and flags it
as partly a legal question. Needs an answer before it needs one in anger.

## 11. Deferred features, with the reason

- **Outbound email** (Phase 2 §2.4) — deferred by the owner in favour of a
  log-an-email action. Trigger for revisiting: evidence he uses the reminder
  list. Sending on his behalf before then is worse than nothing.
- **SharePoint mirror, Plan 4b** — **cut from Phase 1** by the owner on
  2026-09-04. The seam exists (`NotImplementedMirror`), the settings screen
  exists, the sync does not. Nothing depends on it. *Still to record in the
  Phase 1 roadmap doc.*
- **OCR on receipts** — the columns (`source`, `ocr_*`) exist and are unused so
  that adding it later is not a migration against a live table. Engine is
  proven and portable per the reuse spec.
- **PDF receipts render inline** — currently download-only, which is the safe
  answer. Inline would need a sandboxed frame and a tightened CSP.
- **Drag to move a task** — argued against and deferred. It conflicts with
  showing what will move BEFORE it moves, and touch-dragging a bar next to
  other bars at 390px is unreliable. If revisited, the honest version is drag
  on the calendar only, for a task with no dependents.

## 12. Smaller things, recorded so they are not rediscovered

- Reminder rule titles repeat the card they sit on ("Won Basement finish —
  confirm start date" under a card titled *Basement finish*). Right on the
  reminders screen where the project is not in view; wrong on a pipeline card.
  Fix at the template: lead with the verb.
- Days-in-stage could carry a tone threshold — **needs the owner to say what
  "too long" is** before it is guessed at.
- The pipeline's kind filter could be one-tap links instead of a select.
- `Quote sent` column could carry the summed value of sent, unexpired quotes,
  labelled "quoted" to distinguish it from contract value.
- Column headings on the board are not sticky at desktop widths (they are below
  `sm`). Matters once a column is long.
- `purchase_order_id` on `assignments` has no foreign key, because
  `purchase_orders` does not exist yet.
- `expenses.project_id` is `NOT NULL`, where the spec left it nullable —
  overhead with no job is currently unsupported rather than half-supported.
- `expense_taxes.is_recoverable` is a boolean, so partial recovery (a
  50%-claimable meal) cannot be expressed.
